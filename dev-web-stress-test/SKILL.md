# Web 压力测试与性能验收

把一次压测做成"结论可信、可复测、可验收"的工程，而不是跑个工具出个数字。本 skill 沉淀自完整实战（交易门户 + 竞价大厅/详情页 + WebSocket 出价回报，3000 并发验收 + ~6k TPS 容量探顶），覆盖从侦察到报告的全流程。

## 开工先问目标：验收，还是探顶？

- **性能验收**："能不能扛住约定的 N 并发"——阶梯到约定档位为止，M1~M9 对照判定。
- **能力评估（容量探顶）**："能扛住多少、瓶颈在哪"——逐档加压找拐点，产出"拐点并发 × 该点 TPS + 三曲线"。
- 两套方案不同；**拿验收方案直接探顶是最大的坑**（负载低估、无 TPS 列、分片顺序跑……）。探顶任务先读 `references/capacity-probe.md` 过六差距自检。

## 核心工作流（六阶段）

```
① 协议侦察 → ② 方案与指标 → ③ 工具搭建 → ④ 双口径执行/探顶 → ⑤ 实时性专项 → ⑥ 验收报告
```

### ① 协议侦察（先摸清再动手，1~2 小时）

目标：拿到可直接落脚本的接口与报文，而不是猜。按顺序做：

1. **抓真实报文**：内置浏览器打开目标页（Network/页面内 hook XHR/fetch），或 mitmproxy 脚本落盘。SPA 站点可直接下载前端 bundle 静态分析——minified JS 里 `grep` 接口代码（如 `"GP24B0"`、`/xxx-service/api`）、协议常量（WS 帧头、心跳报文、鉴权帧构造函数如 `buildAuthMessage`）。懒加载分片要**全量下载后互扫**，别只看入口 bundle（教训：WS 客户端曾在漏扫的分片里）。
2. **匿名探测**：对每个接口发单发只读请求，确认鉴权边界（哪些匿名可用、哪些需登录态）——匿名可用的接口决定压测是否需要大量账号。**匿名报错 ≠ 参数错**：先补 `Authorization: Bearer` 再下结论（实战：报价队列接口缺登录态被误记"参数需联调"，补上就能用）。
3. **鉴权字段定位**：打印登录响应全字段找 token/FIRMID 类字段（常常藏在登录响应而不是探活接口里）。
4. **实时通道定性**（WS vs 轮询）：看前端定时器常量（`setInterval` 的周期值）与 WS 连接构造；**推送受众必须做对照实验**，不要假设广播——四组实验设计见 `references/protocol-discovery.md`（游客/非参与者/参与者/出价方逐一验证谁收到推送）。结论直接改写压测模型。
5. **列表页/大厅侦察**：真实用户路径是"先列表后详情"，列表页的重查询接口（单发 600ms~1.2s 级）比详情页快轮询更能打 CPU/DB，漏掉会系统性低估负载；报文构造两条铁律（内嵌 JSON 紧凑无空格、每协议必带封装注入字段如 COMPID）见 `references/protocol-discovery.md` §7。
6. **业务写操作语义**：出价/下单类的价格规则（如跟随实时底价 +1 爬梯）、幂等与拒绝文案，决定触发脚本怎么写。

产出：《接口速查表》（接口、参数、鉴权、报文模板、实测 RT）+《实时通道结论》。

### ② 方案与指标

- 用 **M1~M9 指标框架**（见 `references/acceptance-report.md`）把目标翻译成可判定的阈值：首屏 P95、接口 P95/P99、错误率、连接成功率、心跳断连、实时性延迟、长稳。**阈值先给建议值再让业务方拍板**。探顶任务改用能力口径（拐点并发 × TPS + 三曲线，见 capacity-probe.md §4）。
- 负载模型算清三面：首屏洪峰（瞬时）、轮询常态（QPS = 并发 × 人均频率）、长连接面（连接数 + 心跳 + 推送）。实时性指标按侦察结论拆分（如"个人回执延迟"与"他人可见延迟"是两个指标）。
- **登录态接口纳入会话生命周期管理**：token 类会话 ~1h 过期，长跑/长稳/探顶必配续期（会话守护 + 每轮起压前验活重登）；链路校验组第一个采样器就打登录态接口，token 失效立即暴露。

### ③ 工具搭建

- **JMeter + WebSocket Samplers（Luminis 插件）**为主工具，HTTP 与 WS 一个计划覆盖；出价触发源用 Python 复用既有脚本。计划模板见 `assets/jmeter-plan-template.jmx`（全部 `-J` 参数化、线程组默认 0 线程护栏），JMX 落地坑见 `references/jmeter-playbook.md`。
- 执行器模式：`run_round.py`（阶段化执行 + 每阶段 jtl/HTML 报告/汇总 + `--stage` 单场景）；汇总带 TPS 列（探顶/容量评估必需）；实时性测量独立脚本（`scripts/` 有通用件）。
- 启动器：菜单式 bat（双击）+ 命令行快捷方式，方便非技术人员复跑；bat 用 GBK+CRLF，生成脚本注意 BEL 陷阱（pitfalls §Python）。

### ④ 双口径执行（结论可信的关键）

- **口径 A 无缓存最坏模型**：首访拉全部静态资源 → 暴露带宽/静态容量问题。
- **口径 B 缓存模型**：静态资源关闭、思考时间每轮一次 → 干净的 API/轮询/WS 口径，**指标判定以此为准**。
- 场景阶梯（命名与样例工程 run_round.py 阶段表一致）：

| 阶段 | 内容 | 时长 | 备注 |
|---|---|---|---|
| S0 冒烟 | 链路校验，首采样器打登录态接口 | ~2min | 不带病开压 |
| S1~S3 阶梯 | 首页/详情/WS 逐档加压 | 每档 5min | 验收打到约定档位为止 |
| S4 混合稳态 | 验收并发混合负载 | 15~20min | 指标判定主口径 |
| S5 洪峰 | 集合点瞬时爆发 | 短 | **单独跑**（全量汇合会卡其他组） |
| S6 实时性专项 | 出价回执/可见延迟测量 | — | 独立脚本（见 ⑤），不在 JMeter 内 |
| S7 长稳 | S4 节奏持续跑 | 2~4h | 需运维监控配合；勿跨闭市 |
| S4_probe 探顶档 | 验收档起步逐档 +25% | 每档 ~5min 稳态 | 能力评估时叠加；load 档与拐点判定见 capacity-probe.md §3~4 |
- **模拟用户档压不热服务端先算吞吐账**：轮询模型吞吐 = 线程 ÷ 轮询周期（20 标的 × 1s 档 ≈ 50 QPS，服务端并发需求 ≈ 4 个）。打热用 load 探顶档：轮询周期缩 10~20 倍 + 100~200 线程/组，**非 GUI + JTL 落盘**、禁用"查看结果树"（capacity-probe.md §3）。判读：**RT 突增而 CPU 不动 = 连接池/锁排队等串行瓶颈**，比 CPU 打满更有价值。
- **环境异常剔除**：若某轮空载基线整体劣化（如所有接口统一 +500ms），在健康窗口复测同档位，判定用复测数据，劣化另立"环境问题"条目归因——不要让环境噪声污染能力结论。判读前先确认服务端空载基线（单发延迟会随服务端自身负载漂移）。
- 熔断护栏：滚动错误率超阈值自动停压；出价等写操作仅限测试场次且需显式确认。

### ⑤ 实时性专项

- WS 指标：建连/鉴权成功率与 RT、心跳稳定性（超时断连=0）、回执延迟（P50/P95/P99）、到达率。
- 轮询可见性：N 路观察者 1s 档轮询，记录关键字段快照（如 BESTPRICE），与写操作时间戳对齐算可见延迟；**匹配条件要校验语义**（教训：价格相等即满足的条件会提前命中，须以"出价前基线变化"为准）。
- 时钟：出价方与观察者同机记录最稳；跨机先 NTP。测量脚本模式见 `scripts/realtime_measure.py` 与 `references/jmeter-playbook.md`。

### ⑥ 验收报告

按 `references/acceptance-report.md` 的结构产出 Word + md + 十行结论摘要：执行摘要（结论先行）→ 环境 → 方法与口径 → 执行明细（每表标数据来源）→ M 指标对照表（通过/不达标/未测/不适用）→ 实时性 → 已知环境问题 → 整改意见（含技术评估与验证方式）→ 配置对照（如有）。**所有数字来自结果文件，未测写未测，中止写"部分数据"。** 探顶任务报告另含"能力曲线与瓶颈归因"章节（口径见 capacity-probe.md §4：拐点并发 × TPS + 三曲线，不说"最高压到 X"）。

## 铁律

1. **写操作（出价/下单/注册）必须业务方指定测试场次**，触发脚本带显式确认参数；压测前取得书面授权，避开真实高峰与闭市窗口（交易类系统 8:30–17:30），长稳勿跨闭市。
2. **结论要有证据链**：协议结论 = 源码/抓包/实验；性能结论 = 标注来源的结果文件。假设与实测冲突时，以实测改写方案（并记录修订）。
3. **双口径 + 健康窗口复测**，别混在一起统计；两轮口径差异必须在报告里分别呈现。
4. **阈值判定用 P95/P99**，不用平均值——长尾才是验收风险（真实案例：P50=153ms 但 P95=3.5s）。
5. **数据面有时效**：标的/场次清单每天开工先重扫（跨天过期；占位符/TODO 标的 = 压异常分支不是真实负载）；自建场次时长必须覆盖压测窗口；登录态 token 长跑必配续期——开工先验数据新鲜度，再开压。
6. 报告生成后跑 docx postcheck（空白页/封面溢出/表格/目录），修完所有 ❌ 再交付。
7. **敏感信息不进交付物**：账号表/token/FIRMID 不写入报告附录，accounts.csv 等凭证文件不入仓库；交付 Word 前全文搜 token/密码字样，配置里的密码用环境变量或本地不入库文件承载。
