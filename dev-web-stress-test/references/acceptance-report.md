# 验收指标框架与报告规范

## 1. M 指标框架（按系统裁剪，阈值先建议后拍板）

| 编号 | 指标 | 典型阈值 | 备注 |
|---|---|---|---|
| M1 | 首页/首屏加载 P95 | ≤ 3s | 补充 M1b：无缓存首访含静态 |
| M2 | 核心页面首屏 P95 | ≤ 3s | |
| M3 | 高频接口 RT | P95 ≤ 500ms、P99 ≤ 1s | 轮询主角接口在目标 QPS 下测 |
| M4 | WS 建连/鉴权 | 成功率 100%、握手 P95 ≤ 1s、鉴权 P95 ≤ 500ms | |
| M5a | 写操作回执延迟（当事人） | P95 ≤ 2s | 若有广播则为扇出延迟 |
| M5b | 回执/推送到达率 | ≥ 99.9% | |
| M5c | 他人可见延迟（价格/状态） | P95 ≤ 2s | 通常由轮询决定 |
| M6 | 连接稳定 | 心跳超时断连 = 0、非主动断连 = 0 | |
| M7 | 错误率 | < 0.1% | 稳态与洪峰分开判 |
| M8 | 长稳与资源回落 | 2~4h 无泄漏、停压 5min 回落 | 需运维监控配合 |
| M9 | 瓶颈可定位 | 分层监控齐备 | 无源站监控时如实写"部分满足" |

判定词汇：**通过 / 不达标 / 未测 / 不适用**（架构性不存在的指标），带条件的写"稳态通过 / 洪峰不达标"这类复合判定。

## 2. 报告结构（Word + md 同源 + 十行摘要）

```
封面（版本/周期/环境/编制）
一、执行摘要（验收结论）   ← 结论先行：总判定 + 维度结论总览表
二、环境与被测对象          ← 地址/架构/通道/场次参数/压测端
三、测试方法与数据口径      ← 场景模型 + 数据源表（每张表标来源目录与口径！）
四、执行明细                ← 每场景一张分位表 + 失败分类
五、M1~M9 验收对照表        ← 编号|指标与阈值|实测(来源)|判定
六、实时性专项              ← 测量方法/规模/结果表/长尾分析
七、已知环境问题            ← 环境 404、重部署、劣化归因等（影响判读的都写）
八、结论与整改意见          ← 事项|整改意见|技术评估|验证方式（回应业务整改方案并给技术判断）
九、服务器配置对照（如有）  ← 配置角色|实测证据|判定；缺带宽规格这类缺口要点名
附录：数据与脚本索引        ← runs 目录/脚本/方案文档路径
```

## 3. 写作规则

- **数字只来自结果文件**；未测写未测；中止写"部分数据（中止）"；口径不同的数据不合并。
- 术语全文一致；结论与摘要口径一致（改一处同步三处：md、docx、摘要）。
- 整改意见表必须有"技术评估"列——业务给的整改方案要回答"是否真能解决、附什么条件、怎么验证"（示例：CDN 能否顺带解决洪峰问题 → 分面回答：静态面能、API/WS 面本已达标、留网关配置核查）。
- 服务器配置对照：结论通常是"算力达标/充裕"，但**点名规格缺口**（如无带宽规格）与未验证模块；注明"生产以同构复测为准"。

## 4. Word 生成（docx 技能要点；ZCode 环境里技能名为 `documents:docx`）

- 封面 R1 配方 + 目录（TOC 独立分节、页码正文从 1 起）；正文 SimSun 12pt/行距 312/首行缩进 480；表格横向线式、表头着色、`WidthType.PERCENTAGE` 列宽。
- 生成后跑 `postcheck.py` 修完所有 ❌；再跑 `add_toc_placeholders.py --auto` 与 `fix_footer_fields.py`（页脚 PAGE 域 WPS 兼容）。
- 中文引号在 JS 字符串里用 `\u201c \u201d` 转义（skill 强制项）。
- 报告生成器脚本建议留在工程 `tools/generate_report.js`（数据硬编码进内容块），改数据重新 `node` 生成即可。

## 5. 十行《验收结论摘要》模板

1. 总体结论（有条件通过/通过/不通过）
2. 通过项（带关键数字）
3. 不达标项
4. 重要架构发现/修正（如有）
5. 未测项
6. 整改意见（带技术判断）
7. 配置对照结论（如有）
8. 报告与数据位置
