# 容量探顶与能力评估：从"验收达标"到"压出极限"

两种任务目标开工前必须问清，方案完全不同：

| | 性能验收 | 能力评估（容量探顶） |
|---|---|---|
| 回答的问题 | 系统能不能扛住约定的 N 并发 | 系统能扛住多少并发，瓶颈在哪 |
| 负载策略 | 阶梯加到约定档位为止 | 逐档加压直到吞吐平台期/熔断 |
| 判定输出 | M1~M9 对照表（acceptance-report.md） | 拐点并发 × 该点 TPS + 三曲线 |
| 最大坑 | 环境噪声混进结论 | **拿验收方案直接当探顶方案（负载系统性低估）** |

## 1. 六差距自检：验收方案升级成探顶方案

拿验收方案做探顶前逐项自查（实战六项中了五项）：

1. **阶梯有没有探顶档**——止步于验收档位（如 3000）永远探不到极限。主 JMX 线程若全部 `-J` 参数化，加档零障碍。
2. **结果汇总有没有 TPS 列**——没有逐档 TPS 就画不出"并发-吞吐-RT"曲线，拐点无从谈起。每采样器 TPS + 阶段稳态 TPS 都要落盘。
3. **负载模型有没有漏接口**——漏回灌一个轮询接口（如 2s 档报价队列、需登录态）负载就轻 1/3，探顶变"没压到位"。
4. **分片是否真并行**——分片顺序跑，各片时间窗不重叠，合并数据无效；合并时校验时间窗，顺序执行要 WARN。
5. **压测端瓶颈有没有自证**——单机 JMeter ~4k QPS 上限；压测机自己记 CPU，排除"是压测端先顶不住"。
6. **限流/容量约束确认过没有**——单 IP 限流、DB 连接池与容量这些"隐形天花板"没确认前，探顶结果的归因都存疑。

## 2. 负载模型修正：真实路径、重查询、回灌对账

- **真实用户路径从列表页/大厅开始**：先开列表再点详情。列表页的重查询接口（单发 600ms~1.2s）比详情页快轮询（70ms 级）更能打 CPU/DB——只压详情页会系统性低估。重查询单独编线程组（如 200 线程 × 2s 翻页，线程轮转停在不同页）。
- **逐接口对账回灌**：把前端全部轮询接口列成表（周期、鉴权、参数），对照压测计划逐条核对。最容易漏的是"需登录态"的接口——匿名探测失败被误记为"参数需联调"，实际补 `Authorization: Bearer` 就能用。
- **会话池**：登录态接口用 5 个左右账号建会话池轮转，供几十个线程共用。

## 3. "CPU 上不来"诊断与 load 探顶档

模拟用户的 manual 档压不热服务端是常态，先算吞吐账：

**轮询模型的吞吐上限 = 线程数 ÷ 轮询周期**（线程被定时器限速）。20 标的 × 1s 档 ≈ 50 QPS，服务端并发需求 = QPS × RT ≈ 50 × 0.07 ≈ **4 个**——网关/应用/DB 都不会有感觉。

load 探顶档设计：**轮询周期缩 10~20 倍 + 每组线程提到 100~200**（实测 ~4.4k QPS，单机上限内；减量档 ~1.5k QPS）：

| 线程组 | load 档 | 吞吐上限 |
|---|---|---|
| 列表页翻页（重查询 ~0.7s/发） | 200 × 2s | ~75 QPS（≈50 并发压在慢查询上） |
| 首屏（思考 500ms） | 200 | ~1.5k QPS |
| 快轮询 50ms | 200 | ~1.7k QPS |
| 中速轮询 100ms | 200 | ~1.1k QPS |

执行形态：**非 GUI + 每轮新 JTL 落盘**；GUI 大并发吃本机资源，"查看结果树"监听器要禁用（省响应体缓存开销）。

判读三模式（判读前先确认服务端空载基线——单发延迟会随服务端自身负载漂移，上午 70ms 下午可能 400ms+）：

- CPU 爬升 → 正常打热，继续加档；
- **RT 突增而 CPU 不动 → 串行瓶颈**（连接池 maxCon / per-user 锁排队）——比 CPU 打满更有价值的发现；
- 错误率抬升 → 触发熔断护栏，记下档位收手。

## 4. 探顶阶梯与拐点判定

- 阶梯从验收档位起步（如 3000 → 3750 → 4500 → …），每档 ~5min 稳态（ramp 120s），直到增益趋零或熔断。
- 理论 TPS 先给锚点：总并发 × 单线程折算速率（如 0.92/线程），实测以 TPS 列为准。
- 每档记录：每采样器 TPS + 阶段稳态 TPS + P95 + 失败率；汇总末尾生成"能力曲线"表（并发-稳态TPS-增益-P95-失败率）。
- **拐点判定：相邻档 TPS 增益 < 5% 即吞吐平台期（拐点候选）**；P95/错误率陡增处即极限。
- **能力表述口径**："拐点并发 × 该点 TPS + 三条曲线（并发-TPS、并发-RT、并发-错误率）"。不说"最高压到 X"，说"X 并发后吞吐不再增长，瓶颈在 Y（证据）"。

## 5. 分片并行与时间轴对齐

- >3000 TPS 必须分片且**各片并行起压**（单机 JMeter ~4k QPS 上限），N 台压测机同时执行。
- 合并时自动校验各片时间窗是否重叠；不重叠的数据只能丢弃或标"无效口径"。
- 每台压测机另开窗口自证资源：`typeperf "\Processor(_Total)\% Processor Time" -si 5 -f CSV -o loadgen_cpu.csv`。
- 服务端监控（CPU/内存/DB/网关）与 JTL 必须能**时间轴对齐**，否则画不出"哪一档把谁打满"——开工就和运维约定监控粒度与取数方式。
- **服务端监控对齐清单（开压前与运维逐项过，缺项点名写进报告"已知环境问题"）**：
  - 指标：网关 CPU/内存与连接数、应用 CPU/内存、JVM GC 频率与耗时、DB 连接池活跃数/等待数、慢查询计数、网络带宽；
  - 粒度：采样 ≤15s 才能对齐 5min 一档的阶梯窗口（1min 粒度只够看趋势，归因不了单档）；
  - 取数：谁导出、什么格式、时间戳字段与时区——开压前先试取一次，别等压完才发现没数据。

## 6. 测试数据面：标的/场次准备与时效

探顶要打热，数据量要跟上（20 个标的可能是 3000 验收口径，探顶需要 30+）：

**三步补齐**：
1. 盘点自然池：扫描当前可用标的（可查询/竞价中）；
2. 缺口自建：批量自建竞价场次，缺口 +20% 损耗余量；报价开始时间默认 now+10min，**时长必须覆盖整个压测窗口**；
3. 校验：逐个探测详情/行情接口可用性。

**口径分级**：只读场景（首屏/轮询/WS）标的"可查询"即可；出价等写操作场景才要求"竞价中"。

**时效铁律**：
- 开闭市窗口（如 8:30–17:30），压测勿跨闭市；
- **标的清单跨天过期**（详情/队列接口对非当日场次报错）——每天开工先重扫，别信昨天的 CSV；清单只剩几行时当事故处理；
- **占位符/TODO 标的 = 压无效场次**：服务端大概率走异常分支，压出来的不是真实业务负载。

## 7. 会话生命周期（登录态负载的隐藏故障）

- token 类会话 ~1h 过期；探顶/长稳/多轮长跑必配续期机制。
- 模式：会话守护进程（每 N 分钟查年龄 + 抽样验活，失效自动重登）+ 执行器每轮起压前验活重登。
- 会话 CSV 被 JMeter 占用时：续期写 JSONL、跳过 CSV 并告警——已起压的计划不受影响。
- 链路校验组（S0）第一个采样器就打登录态接口，token 失效立即暴露，不会带病开压。

## 8. 写操作容量场景（探顶的另一半，最容易整块遗漏）

"100 用户稳态出价 + 1s 冲刺"这类写容量场景在验收方案里最容易没有代码。安排在只读探顶之后单独执行：触发源用脚本实现业务语义（爬梯出价：无报价=起拍+1，有报价=当前允许价）；容量口径 = 稳态写 TPS + 冲刺完成率 + 回执延迟（P95）。写操作仅限测试场次 + 显式确认（SKILL.md 铁律 1）。

> 状态：截至 2026-10 为方案设计，尚未经完整实战验证——稳态写 TPS 量级、冲刺完成率典型值待首跑回填；触发源实现可参考样例工程 `autotest\perf\s6_measure.py` 的出价适配（爬梯定价），独立写加压器参考 `portal_stress.py` 的熔断模式。
