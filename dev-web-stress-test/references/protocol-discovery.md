# 协议侦察手册：把被测系统摸到"可落脚本"

原则：**所有协议结论必须有源码/抓包/实验三者之一的证据**。以下手法按性价比排序。

## 1. 前端 bundle 静态分析（SPA 站点首选，零打扰）

下载入口 HTML → 提取 `/assets/*.js` 全量下载（**含分片互相引用的懒加载分片**，对所有分片再扫一遍引用关系）→ grep 关键模式：

| 找什么 | grep 模式示例 |
|---|---|
| 业务接口代号 | `"(GP\|MT\|ZB)[A-Z0-9]{2,6}"`、`/xxx-service/api` |
| WS 接入地址 | `wss?://`、`new WebSocket(`、`getWebsocketUrl` |
| 心跳/帧协议 | `HEARTBEAT`、`SOCKET_HEADER_TAIL`、`buildAuthMessage`、`parseSocketMessage`、`substring(1,5)`（帧类型切片） |
| 轮询周期 | `setInterval(` 后追常量定义（minified 里是 `Qi=1e3` 这类短名，顺着变量找） |
| 鉴权构造 | `TOKENID`、`USERID`、`AUTHSTR`、`FIRMID` |

实战教训：WS 客户端曾在入口 bundle 之外的分片里——**只扫入口 bundle 会漏**。另外 minified 常量（如 `SOCKET_HEADER_TAIL="00W2..."`）直接就是压测脚本要的协议常量，抠出来原样用。

## 2. 匿名探测（定鉴权边界）

对每个接口发单发只读请求（注意 Content-Type 带不带 charset 的坑），记录：

- 是否匿名可用（决定压测要不要批量账号）；
- 错误码语义（GB2004=未登录、001000=服务器异常/协议格式错）；
- 响应里的时间戳/seqno 字段（可做延迟测量对时）。

```python
# 统一指令接口类站点的典型探测（form-urlencoded + URL 编码 JSON 数组）
d = json.dumps([{"api": "GP24B0", "params": {...}}], separators=(",", ":"), ensure_ascii=False)
body = ("directives=" + urllib.parse.quote(d, safe="")).encode()
req = urllib.request.Request(url, data=body, headers={
    "Content-Type": "application/x-www-form-urlencoded; charset=UTF-8",
    "X-Requested-With": "XMLHttpRequest"})
```

## 3. 鉴权字段定位

登录响应的字段全集常与探活接口不同（实战：FIRMID 在登录响应里，MT1120 探活里没有）。打印登录响应全部键值再定 WS 鉴权帧怎么拼；WS 鉴权常分游客帧/登录帧两种（如 F409/F408），**游客帧通常可以固定常量直发**，压测主负载因此零账号。

## 4. 实时通道定性：轮询 vs WS，以及"推送发给谁"

- **轮询**：前端 `setInterval` 周期常量 + 页面 XHR hook 实测（hook fetch/XHR 打点即可看到真实频率）。
- **WS**：连接后只发鉴权帧 + 心跳、无订阅帧的服务端，推送是"广播"还是"定向"**必须做对照实验**。四组实验设计（实战验证有效）：

| 实验 | 观察者身份 | 刺激 | 结论用途 |
|---|---|---|---|
| 1 | 游客（游客鉴权帧） | 触发一笔写操作 | 游客收不收业务推送 |
| 2 | 带 token 但未发登录鉴权帧 | 写一笔 | 排除"token 本身够用" |
| 3 | 登录态非参与者 ×2 + 写操作方 ×1 | 写一笔 | 区分"广播给登录用户"与"只发当事人" |
| 4 | 登录态老参与者 ×2 | 由第三方写一笔 | 确认其他参与者是否收到 |

实战结果示例：只有本次出价方收到 2601 回执 → WS 是"个人回执"通道，无广播扇出 → 原"扇出延迟"指标作废，拆成"回执延迟"与"他人可见延迟（轮询）"。**这类结论直接改写压测模型和验收指标。**

## 5. 写操作语义（做触发源前必查）

- 价格/数量规则：实战是"跟随实时底价爬梯"（无报价=起拍+1，有报价=当前允许价）；固定价格会被拒。
- 拒绝文案里的兜底信息（如"不可高于 X 元"）可反推允许价。
- 响应确认字段（订单号、状态），记录写操作时间戳 T0 供延迟测量。

## 7. 列表页/大厅侦察（真实路径的起点）

真实用户路径是"先开大厅/列表页，再点详情"——只侦察详情页会漏掉列表页的重查询接口，而它们才是最能打 CPU/DB 的主力（实战：大厅主列表单发 600~760ms、公告列表 850~1170ms、平台统计 ~1064ms，对比详情页轮询 70ms）。

- 从入口 bundle 顺着路由组件找列表页的全部首屏调用与翻页/刷新触发时机；逐个匿名探测（鉴权边界常有差异：主列表匿名可用，公告类接口需要特定业务参数如 ITEMSCODE）。
- **两条报文铁律（踩过的坑）**：
  1. **指令报文内嵌的 JSON 字符串必须紧凑无空格**——`json.dumps` 要显式 `separators=(",", ":")`，默认带空格会撞自研 JSON 解析器报 `001000 Missing value. at character N`；
  2. **浏览器 postAPI 封装自动注入的字段（如 COMPID）手工构造报文时必须补齐**，漏了报 001000/GB2001。
- 分页/翻页参数（PAGESTART 类）按线程轮转取不同页，模拟用户停在不同页。
- 落地形态：重查询接口单独编线程组（如 200 线程 × 2s 翻页）——QPS 不高但并发压在慢查询上，对 DB/连接池的杀伤力远大于快轮询。
