# 00 · 链路模型与层界证据

## 1. 四层五跳

| 层 | 角色 | 典型组件 | 典型故障模式 |
|---|---|---|---|
| **L0 客户端** | APP / 小程序 / Web | SDK、本地缓存、重试逻辑、WebSocket / 长连接 SDK | 弱网重传、SDK 重试风暴、版本兼容、本地 DNS 污染、心跳被系统休眠掐断（移动端） |
| **L1 Mids** | 接入中间件层 | API 网关、鉴权、限流熔断、协议转换（HTTP↔Socket）、长连接接入与会话保持、负载均衡 | backlog 满、限流误伤、网关线程打满、长连接空闲被回收、TLS 握手开销、路由到错误实例 |
| **L2 DS** | 分发 / 数据服务层 | 路由编排、聚合、缓存、报文转发、连接池 | 连接池耗尽、下游慢导致线程堆积、缓存击穿、报文转发丢字段、超时配置层层放大 |
| **L3 后端服务** | 领域业务服务（Java 为主） | Spring Boot 服务、DB、Redis、MQ、定时任务 | 慢 SQL、锁等待、GC、线程池打满、死锁、大对象序列化、定时任务抢资源 |
| **L4 第三方** | 外部依赖 | 银行 / 交易所 / 支付 / 短信 / 外部行情，常由 C/C++ 或 Go 网关对接 | 对端限流、证书过期、DNS 抖动、对端维护窗口、报文格式不兼容、对端"收到了但幂等去重" |

## 1.5 负载均衡层（LB 链）——排障时最先被忽略、最后才被想起的一层

每一跳之间都可能挂着 0~3 级 LB，串成一条链。**链的每一级都有自己的 idle timeout、健康检查、连接复用与超时配置**，任何一个都能单独制造故障。

### 四种常见形态与它们的典型坑

| 形态 | 常见产品 | 层级 | 典型坑 |
|---|---|---|---|
| **客户侧硬件 LB** | F5 BIG-IP / A10 / 深信服 / Radware | 四层为主，常带 SSL 卸载 | **idle timeout 通常在 300~600s 且由客户网络组掌握，你改不了也看不到**；SNAT 后源 IP 丢失；连接复用（OneConnect）会让多个客户端连接复用同一条后端连接；SSL 卸载后后端看到的是 HTTP，长连接语义被改写 |
| **自建软件 LB** | Nginx / HAProxy / Envoy / LVS | 四层（stream）或七层（http） | `proxy_read_timeout` **默认 60s**；`keepalive_timeout` 默认 75s；`proxy_http_version 1.1` 没配则 upstream 长连接不生效；被动健康检查 `max_fails/fail_timeout` 会在后端偶发慢时**误摘除**；`upstream` 没记录 `$upstream_addr` 就没法做实例级定界 |
| **云 LB** | 阿里云 SLB / 腾讯云 CLB / AWS ELB-NLB | 四层 or 七层 | idle timeout 各有默认值（CLB 默认 900s、经典 SLB 可能更短）；**跨可用区挂载会引入额外 RTT**；安全组与健康检查端口配置错误导致后端被摘除；连接数/带宽规格上限被打满 |
| **容器/服务网格** | K8s Service(iptables/IPVS) / Istio sidecar / 服务发现 | 四层 + 七层 | kube-proxy 的 `sessionAffinity` 默认 None（长连接落到随机 Pod）；滚动发布时 endpoints 更新有延迟，旧 Pod 已删但 iptables 规则未同步 → **Connection refused 尖刺**；sidecar 自身的连接池与超时（Envoy 默认 connect timeout 5s / idle timeout 1h） |

### 集群形态（Mids / DS / 后端都可能是 N 实例）

集群带来的三个额外故障面：

1. **单实例故障被聚合稀释**：成功率 99.5% 看着还行，但按实例拆开可能是 3 台里 1 台成功率 98.5%。表现为"偶发"。
2. **发布残留 / 版本漂移**：集群里有的实例是新包有的是旧包，表现是"同一请求有时对有时错"。
3. **本地状态不一致**：本地缓存、本地会话、本地令牌桶限流——请求落在 A 上有、落在 B 上没有。

**取证必须按实例维度**：Nginx `$upstream_addr`、网关日志里的 `backend` 字段、服务注册中心的实例列表、K8s `kubectl get endpoints`。

## 3. traceId 传递规范（定界的前提）

- 客户端每次请求生成 `traceId`（或由 L1 生成后回传），**逐跳透传**，不允许某一跳重新生成。
- Socket 长连接场景，用**报文流水号 / 会话号**做等价物：客户端本地记录发送流水号与时间戳，服务端记录接收流水号。两端按流水号对账是最硬的证据。
- 每跳日志必须同时打印：`traceId | 上游耗时 | 本跳耗时 | 下游耗时 | 结果码`。
  - **本跳耗时 − 下游耗时 = 自身处理耗时**，这个差值异常大就是本跳有问题。
- 异步/MQ 场景：traceId 必须写进消息头，消费侧继续透传，否则链路断在 MQ。

## 4. 层界证据清单（每层四件套）

对每一层，都要能拿到这 4 个数：

| 指标 | 用途 | 拿不到时的兜底 |
|---|---|---|
| **入向请求数**（按 traceId/接口 维度） | 判断报文到没到这层 | 网关 access log 计数、`grep -c` 日志 |
| **出向请求数** | 判断这层有没有往下转发出去 | 下游层的入向计数、本层 outbound 日志 |
| **耗时分位** P50/P95/P99 | 判断慢在哪 | `awk` 提取 access log 耗时列算分位 |
| **错误码分布**（超时 / 4xx / 5xx / 拒绝） | 判断失败类型 | `grep` + `sort | uniq -c` |

### 定界判据（背下来）

```
本层 in 有、out 无        → 本层丢弃（限流 / 鉴权 / 报文校验 / 队列溢出 / 熔断）
本层 in 有、out 慢        → 耗时吃在本层或它的下游（用"自身处理耗时"区分）
本层 in 无、上游 out 有   → 报文在链路上丢了（网络 / LB / 半开连接 / 防火墙）
本层 in 慢、上游 out 快   → 上游到本层之间排队（backlog / 连接池 / 线程队列）
两端都有但耗时差巨大     → 序列化 / 网络 / Nagle+延迟ACK / 跨可用区

【集群专属】
聚合成功率正常、某实例异常   → 单实例故障（发布残留 / 磁盘满 / GC / 未注册 / 本地缓存不一致）
同一请求时好时错           → 版本漂移 或 本地状态不一致，按实例 + 版本号分组
错误集中在固定客户端 IP     → 客户侧链路（专线 / 客户硬件 LB / 地域），不是你的集群问题
错误均匀分布、随实例重启消失 → 实例级泄漏或启动加载不全
```

### 实例级定界的取数动作

```bash
# Nginx：按 upstream 实例聚合成功率与耗时（日志格式必须含 $upstream_addr / $upstream_response_time）
awk '{print $upstream_addr_field, $status_field}' access.log | sort | awk '{c[$1"|"$2]++} END{for(i in c) print i, c[i]}' | sort -k3 -nr | head -30
# 只看 5xx 落在哪台
awk '$status ~ /^5/ {print $upstream_addr_field}' access.log | sort | uniq -c | sort -nr
# K8s：确认 endpoints 与 Pod 实际状态是否一致
kubectl get endpoints <svc> -o wide; kubectl get pod -l app=<app> -o wide
# 服务注册中心：是否有实例未注册 / 处于半死状态（心跳在但处理不了）
```

## 5. 超时配置的"层层放大"陷阱

常见配置链：客户端 30s → L1 网关 25s → L2 20s → L3 15s → 第三方 10s。

- 上游超时必须 **大于** 下游，否则下游还没返回上游就断了，日志里会出现**上游超时、下游成功**的诡异组合（对账不平的元凶）。
- 检查清单：客户端 SDK 超时 / L1 路由超时 / L2 连接池超时（connect + read 分开配）/ L3 HTTP 客户端超时 / L4 第三方约定超时。
- **connect timeout 与 read timeout 必须分开配置**，混用一个值会让建连问题伪装成业务超时。
- **LB 链上每一级都要进这张表**，它同样有自己的超时，且常常是最短的那一个。

### 各级超时 / idle 参数对照（配置时逐级对齐）

| 级 | 关键参数 | 常见默认 | 说明 |
|---|---|---|---|
| 客户端 SDK | connectTimeout / readTimeout | 各 SDK 不同 | 必须显式配置，别用默认 |
| 客户硬件 LB（F5/A10） | idle timeout / TCP profile | 300s（常见） | **你改不了**，只能让心跳适配它 |
| 云 SLB/CLB | 连接空闲超时 | 900s（各云不同） | 控制台可查可改 |
| Nginx 七层代理 | `proxy_connect_timeout` 60s / `proxy_send_timeout` 60s / **`proxy_read_timeout` 60s** | 60s | 504 的头号来源 |
| Nginx 客户端侧 | `keepalive_timeout` 75s / `keepalive_requests` 100 | 75s | 短于上游心跳周期就会频繁重建 |
| Nginx upstream 长连接 | `proxy_http_version 1.1` + `proxy_set_header Connection ""` + `keepalive N` | 默认不复用 | 没配则每次请求新建后端连接 |
| Envoy / sidecar | connect_timeout 5s / idle_timeout 1h | — | 网格里的隐藏超时 |
| 应用 HTTP 客户端 | connect / read / connectionRequest(等池) | — | 三个都要配，`connectionRequest` 超时最能暴露池太小 |

**对齐规则**：客户端心跳周期 < Nginx keepalive < 云 LB idle < 客户硬件 LB idle；同时上游读超时 > 下游读超时。
