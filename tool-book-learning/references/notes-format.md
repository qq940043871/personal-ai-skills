# 章节笔记 Markdown 格式（提取阶段输出契约）

提取阶段每一章写一个 `notes/chNN.md`（NN 为两位章号），**必须严格遵循以下结构**，
`build_site.py` 依赖这些标题层级做解析。正文一律中文。

写入前先跑一遍：`python scripts/audit_notes.py --book <书籍文件夹> --profile <tech|prose>`。

## 技术书（profile=tech）模板

```markdown
# 第N章 章节标题
> 一句话概括本章讲什么、解决什么问题（不超过60字）

## N.N 节标题
### 知识点标题
知识点正文。可多段、可用列表；关键术语用 **加粗**，代码/类名用 `反引号`。
技术细节要具体（类名、方法名、参数、数字、协议字段），不要泛泛而谈。

### 另一个知识点
- 要点列表也可以
- 保持信息密度

## N.M 下一节标题
### 知识点
……

## 核心概念
| 概念 | 说明 |
| --- | --- |
| 名词/类名/协议 | 一两句话定义，说清本质 |
| 另一个概念 | …… |

## 代码要点
```java
// caption: 这段代码在讲什么（一句话）
// 精简后的关键代码，保留核心逻辑
public class Example {
    // ...
}
```

```text
// caption: 可以是配置片段/报文示例/流程
……
```

## 常见误区与深入理解
- 常见的错误理解是……实际上……          ← 不要写 `- **误区**：` 前缀，模板自带 ⚠ 图标
- **深入**：进阶理解/底层机制是……        ← `- **深入**：` 要保留，模板没给图标

## 自测问题
1. **Q**：问题内容？
   **A**：答案内容。
2. **Q**：……
   **A**：……

## 本章收获
- 读完本章应该能做到/理解的两三条结论
```

## 非技术书（profile=prose）唯一区别

第 2 个固定小节叫 **`## 关键论断`**（不是「代码要点」），其余四级完全一致。
内容用 ```text 块承载公式 / 架构分层 / 矩阵 / 清单，首行仍写 `// caption: 说明`。

用 `--profile prose` 编译即可，**不需要复制脚本、不需要打补丁**。

## 规则

1. `## ` 二级标题只允许两类：**节标题**（如 `## 2.3 网络I/O工作机制`）和 5 个固定小节
   （核心概念 / 代码要点(关键论断) / 常见误区与深入理解 / 自测问题 / 本章收获）。
   出现第三类 `##` 会让解析错位，站点上表现为章节内容串位。
2. `### ` 三级标题 = 知识点卡片标题，其下内容即卡片正文。每个知识点 80-250 字为宜。
   `###` 允许出现在固定小节里（如「核心概念」下再分卡片），build_site 会正确统计。
3. 代码块语言标 `java`/`xml`/`text` 等；**第一行必须有 `// caption: 说明`**
   （xml/text 用 `<!-- caption: -->`）。缺 caption 是最高频的审计错误。
4. 自测问题每章 3-6 道，答案要能从本章内容推出。**Q 与 A 必须成对**，
   历史上出现过 22 条答案混在题干里、点「查看答案」展开空盒子的事故。
5. **忠于原书**：不编造原书没有的技术结论；书中的表格/报文/参数尽量转成 markdown 表格或代码块。
6. 章末的"总结"节内容并入「本章收获」，不必单独成节。
7. H1 建议写成 `# 第N章 标题`。章号前缀支持 `章/篇/部/部分`（合集类书写「第N篇」也能正确显示），
   但写成纯描述性标题时站点上不显示章号（审计会给 WARN）。
8. **OCR 来源（`pages_ocr/chNN.txt`）先去噪再写**：OCR 会把形近符号认错（`Yuyi$Inner`→`YuyiSInner`、
   `0/O`、`1/l`、全半角括号）、会把换行处的句子断成半截、会把图内的散落标签按乱序拼在一起。
   写笔记前先通读还原成正确的语义与代码形态，**别把 OCR 的错别字、断行、乱序标签带进卡片**。
   manifest.json 里 `need_vision=true` 的页是图表页，必须读 `pages_ocr/vision/chNN/pNNNN.png` 补图语义。
