# 知识库质量审查与修复战役

本流程源自 2026-11-08 技术库实战：三代理审查 14 专题 → 8 代理三批修复 11 个问题目录 → 独立终验 → 记忆沉淀。它把那次战役的可复用部分固化为标准打法。

## 总流程（四阶段，不可跳过阶段 0）

```
阶段0 摸底与安全定级 → 阶段1 质量审查（多代理） → 阶段2 修复战役（分批派发） → 阶段3 终验与沉淀
```

核心判断：**先定级再动手**。哪些目录被 gitignore 决定了删除策略；哪些文件是存根决定了修复策略。跳过阶段 0 的修复战役必然发生不可逆事故。

---

## 阶段 0：摸底与安全定级

**1. 大小分布扫描**（识别存根与深度，给出每个专题的健康画像）：

```bash
for d in <专题目录>/; do
  tiny=$(find "$d" -name "*.md" -size -2k | wc -l)
  big=$(find "$d" -name "*.md" -size +8k | wc -l)
  total=$(find "$d" -name "*.md" -exec wc -c {} + | tail -1)
  echo "$d | <2KB:$tiny | >8KB:$big | $total"
done
```

判读：`<2KB` 占比高 → 大概率存根/占位符；`>8KB` 占比高 → 深度内容为主。**小文件不能只看数量，必须抽读定性**（完整短笔记 / 导出残缺 stub / 目录索引页，三者处理方式完全不同）。

**2. git 保护级别分类**（决定删除策略，一次查清）：

```bash
git check-ignore -v <每个问题目录的样例文件>
```

- **git 跟踪目录**：改动有 git 历史兜底，改名用 `git mv` 保历史，改完**不 commit**（留给用户审）。
- **gitignore 目录**：`rm` 即永久消失。铁律：**一切删除先 `mv` 归档**到 `library/_备份元数据/_<YYYY-MM-DD>修复归档/<原目录名>/`（保持相对结构），归档区加 README 说明。

**3. 确认既有事实**：查项目 memory（四源整理方案、为知迁移等记忆）——已知缺陷（如"为知导出丢正文数字与配图"）、已知密码文件、已执行的查重清理，避免重复劳动或推翻既定决策。

**4. 并发约束**：子代理每批 ≤3 个并行（用户环境有并发限制），按"最重的先走"排批次。

## 阶段 1：质量审查（多代理）

**派发方式**：3 个 general-purpose 代理并行，每个负责一摊相近目录。审查 prompt 必须包含：抽样策略、九类问题清单、评级标准、证据要求。

**抽样策略**（每个目录）：`ls` 看文件名规律 → 精读 4-6 篇 = 最大的 2-3 篇 + 中等 1-2 篇 + 最小的 1 篇；小文件额外抽 5-8 篇判性质。精读要通读全文，不是只看开头。

**九类问题清单**（审查与修复共用）：
1. 悬空数字（`只有 % 的软件项目`）与被啃代码（`if (size() >){`）
2. 截断（文章戛然而止、自称 100 问实存 46 问）
3. 未转换的平台 XML/标记（`<callout>`、`<sub-page-list>`、`:::info`、`<title>`、`<font>` 噪音）
4. 存根/空壳/空目录
5. 导出噪音（`复制代码`、AI 长 alt 描述）
6. 格式（围栏未闭合、BOM、嵌套围栏吞文）
7. 结构错位（H1 课号与文件名不符、题不对文、编号冲突双 01）
8. 名不符实（目录名与内容不符、README/总纲与实际篇数不符、状态标记失真）
9. 安全（明文密码、密钥、内网地址+账密）

**评级**：优（可直接发布）/ 良（硬伤需修）/ 中（当索引用，别照抄）/ 差（空壳名不副实）。每级给一句话总评 + 问题清单（附文件名和证据引文）。

**收口原则**：审查报告回来后，**最戏剧性的结论必须亲自抽验**（读原文件 grep 实锤），再给用户最终评估。子代理的结论是模型输出，不是事实。

## 阶段 2：修复战役（分批派发）

每批 3 个代理，批次间不互相依赖。修复 prompt 的完整模板见 `references/repair-playbook.md`（含分档细则、各专项模式、错误教训），要点：

**每个修复 prompt 必须写入的铁律**：
1. **绝不编造**：数据类数字（统计/百分比/性能值）绝不可推测补全；空壳不生成假正文；缺失篇目不补写。
2. **分档修复**：可推断的机械值（`int i = 0`、`sort -k2` 按列语义）补值并加注释标注；不可推断的数据改定性表述；无法修复的如实标注"导出缺失"。
3. **归档优先**：gitignore 目录的删除/存根清理，先 mv 到归档区；git 跟踪目录用 `git mv`。修改类操作也建议先备份原稿到归档区 `_修复前原稿/`。
4. **自检清单**：任务收尾必须跑 grep 自检（残留模式清零、抽 N 篇通读、围栏平衡），报告 ≤500-600 字要证据不要空话。

**改名操作**（改动面最大，单独流程）：`git mv` → 按"目录/子路径"全串匹配 grep 旧名（**裸文件名 grep 会大量误报**，如"系统架构/模型加载"是常用词）→ 修复 wiki/README/CLAUDE/其他库引用 → 重建 `tree.json`（`python library/build_tree.py`）→ 验证新名在、旧名无。

**跨库影响**：改动的目录若被六库其他文件引用（如小说卷、README 导航），引用修复要一并做，这是"整目录删除前逐文件核对孤本性"教训的镜像。

## 阶段 3：终验与沉淀

**1. 独立终验**（不信子代理自检，用 `scripts/verify_kb.py`）：

```bash
python ~/.agents/skills/tool-kb-audit-repair/scripts/verify_kb.py --root "library/技术" --archive-root "library/_备份元数据"
```

覆盖：密码残留、存根残留、XML/`:::` 残留、空目录、围栏平衡、疑似悬空数字（人工复核项）。输出按 PASS/FAIL 分组。**归档区要排除在密码扫描的"事故"判定外但要单独点名**（见下）。

**2. git 复核**：`git status --porcelain` 逐项核对改动是否符合预期（重命名数、修改数、删除数），有意外删除立即排查。不 commit。

**3. 记忆沉淀**（不沉淀 = 战役白打一半）：更新项目 memory（`note-organization-plan.md` + `MEMORY.md` 索引行），必须包含：
- 结果数字（修复量、归档量、tree.json 篇数）
- ⚠️ 未决事项（密码轮换、未 commit、归档区含密码原稿待删）
- **新教训**（编号追加到既有教训列表，这是最值钱的部分）

**4. 向用户报告**：表格汇总各目录修复成果 → 终验结果 → 安全事项单列 → 下一步建议（commit?密码轮换?）。

## 血泪教训（本战役实证，新战役前必读）

1. **`.md_d` 等怪后缀不一定是重复**——实战中 15 个 `.md_d` 目录全是系列续篇（如 001 目录装 002-010），差点误判归档。先看内容与同名文件的关系再动手。
2. **裸文件名 grep 查入链 = 大量误报**，必须按"目录/子路径"全串匹配。
3. **"两目录是重复关系"的粗结论不可信**，整目录删除前逐文件核对孤本性（rocketmq 孤本险些误删，git 恢复）。
4. **语雀/为知导出天生丢数字与配图**——修复靠分档（补值/改写/标注），永远不编造；配图可 SVG 重绘，数字只能改写或标注。
5. **查重清理会留下空壳框架**——删内容时同步删壳（stub+空目录），否则留下"146 篇"的名不副实目录（Agent开发前车之鉴）。
6. **状态标记会失真**——"🔄 待完成"的 48 篇实际全写完了。README/总纲/版本历史都要与磁盘实际对齐。
7. **密码文件处理预案**：归档原稿（归档区 README 警示"用后即删"）→ 原文件替换脱敏说明 → 提醒用户轮换。技术库外的密码痕迹（如工作/客户跟踪）也要报告，虽不在当次范围。
